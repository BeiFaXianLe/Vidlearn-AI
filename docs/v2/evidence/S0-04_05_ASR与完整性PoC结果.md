# 一、S0-04 长音频 ASR：**通过（含 1 个必须修复的缺陷）**

## 1.1 验证内容
FFmpeg 切片 → 逐片 faster-whisper 识别 → 合并 + 全局时间偏移。

## 1.2 结果

| 指标 | 值 |
|---|---|
| 源音频 | 74.00s |
| 切片 | 3 段（0s / 30s / 60s，每片 30s） |
| ASR 单元 | 14 条 |
| 推理耗时 | 14.34s |
| **RTF** | **0.194**（约 5.2x 实时） |
| 时间戳越界 | 0 |
| 时间戳重叠 | 0 |
| 边界对齐 | ✅ 每段首条 start 精确等于段偏移（0.00 / 30.00 / 60.00） |

## 1.3 发现的缺陷（必须修复）

**切片硬切会截断/重复句子**：

| 边界 | 现象 |
|---|---|
| 30s 处 | 前段末 "语音识别把字幕转写出来," 与后段首同一句重复 |
| 60s 处 | "工作站" 被切成 "工作" + "作战的架构设计" |

→ **S4-04/05 实现约束**：
1. 切片需**重叠 1–2 秒**（overlap）；
2. 合并时做**边界去重**（文本相似度比对，重叠区取一次）；
3. 或改用 VAD 按静音切分，避免切在词中间；
4. 时间戳合并后需校验单调、不重叠、不越界（本 PoC 已实现校验器，可直接复用）。

## 1.4 其他注意事项
- **首次模型加载 600s**：这是首次从 HF 下载 `faster-whisper-small` 的一次性开销（约 460MB），**不是推理耗时**。正式产品必须：
  - 预置/预下载模型到本地；
  - 或设置 `HF_TOKEN` 提升下载速度；
  - 加载超时与进度提示要设计。
- Windows 下 HF 缓存无法用符号链接会占更多磁盘（已有告警），需注意存储配额。

# 二、S0-05 媒体完整性：**通过**

## 2.1 判定器设计（多指标，非单一）

1. ffprobe 能否解析容器结构
2. 容器时长 / 视频流时长 / 元数据时长 差值（>2% 或 >1s 记异常）
3. 完整解码 `ffmpeg -f null -` 退出码
4. 尾部 2 秒解码（验证可解到结尾）
5. 音视频流存在性（用途相关：无音轨则 ASR 不可用）

## 2.2 样本结果

| 样本 | 判定 | 依据 |
|---|---|---|
| A 正常 MP4（有音轨） | ✅ `verified` | 全指标正常 |
| B 截断 MP4 | ✅ `invalid` | `moov atom not found` |
| C MKV（内嵌字幕+音轨） | ✅ `verified` | 流时长缺失时退化用容器时长，逻辑正确 |
| D 无音轨 MP4 | ✅ `likely` | 可播放但 ASR 不可用（修正后正确） |
| E 伪装 .mp4（文本） | ✅ `invalid` | 容器无法解析 |

## 2.3 关键实现发现

1. **MKV 的视频流级 duration 常为 null** → 不能依赖流时长，必须退化到容器时长。
2. **"无音轨"不应判 verified** → 对 ASR 场景应为 `likely`（可播放、不可转写）。这要求完整性判定**带用途上下文**。
3. **单一指标会误判** → 截断文件 FFprobe 直接报错好识别，但**部分截断（moov 完整、数据不全）未必报错**，必须靠尾部解码 + 时长比对补足。
