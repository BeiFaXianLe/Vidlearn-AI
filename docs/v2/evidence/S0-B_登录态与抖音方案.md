## 二、B站字幕：为什么"不想手动导入"必须靠登录态

实测（匿名，无 Cookie）：

```
GET /x/player/v2?aid=80433022&cid=137649199
-> code=0, subtitle.subtitles = []
GET /x/player/wbi/v2?...  同样 []
```

对照 CSDN 那篇介绍的工具 **BiliBiliCCSubtitle（ccdown）**：它的原理就是调这个 CC 字幕 API 再转 SRT。**它能用，是因为它跑在用户已登录的浏览器 Cookie 上**——不是因为它有魔法。7 stars、2021 年后停更（pushed 2020-07），不适合直接依赖。

**所以：登录态 = 拿到平台字幕的前置。** 这条已写入设计：字幕来源优先级改为
① 登录态平台字幕（人工/AI）→ ② 视频内嵌字幕轨 → ③ 本地 faster-whisper ASR → ④ 云端 ASR（可选）。

### 它的 FAQ 关键原文（已核对）
- **「需要我自己的 Cookie 吗？」→ 不需要**。默认自建游客身份池；
- **B站游客身份用纯 HTTP 就能领到 `buvid3`，不需要浏览器**；
- 抖音/TikTok 需要无头浏览器（`browser-rpc`）生成 `ttwid` 等；
- 「机器封号吗」→ 游客身份烧了就烧，只有登录态才用你的号；
- **它自己承认**：自动隔离通常违反平台条款，自托管工具无法替你强制。

### 对 VidLearn 的处置建议
- **可以采纳**，但定位为「**可选增强适配器**」，与主链路解耦：
  - `DouyinAdapter` 通过其 REST API（本地自托管）调用，不内嵌其源码（保持许可证清爽）
  - 默认关闭；启用时 UI 明示「使用第三方采集服务，账号与合规风险自担」
  - 失败时降级为「仅保留元数据 + 提示用户上传本地文件」
- 备选更轻量：`jiji262/douyin-downloader`（12.5k★, MIT, Python, SQLite 去重）——单条/批量下载够用，工程量小
- **不建议**：`JoeanAmier/TikTokDownloader`（GPL-3.0，传染）

## 四、架构影响（相对 S0-A 的变更）

1. **字幕主路径改为"登录态优先"**，ASR 变为兜底/无字幕场景主力。
2. **新增凭据管理模块**（需改 PRD §11）：
   - 存储：本机加密（如 DPAPI / AES + 本地密钥），**绝不入日志、绝不外传**
   - 使用：仅作为 yt-dlp / 采集器请求头的 cookie
   - 生命周期：可一键清除；失效自动提示重新登录
3. **凭据合规条款改写**：从「不使用或保存 Cookie」→「仅在用户明确授权下、本地加密保存、仅用于本人请求、不外传、可随时删除」。
4. **新增 `CredentialProvider` 抽象**：`none`（默认）/ `bilibili_cookie` / `douyin_api`。
5. **抖音不再是占位**，但仍是 P1（可选增强），不阻塞 S1–S6 主链路。
